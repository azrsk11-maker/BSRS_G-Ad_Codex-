# Private owner mailbox review candidate

This implements the manual owner workflow approved in issue 10, under [DEC-09](../../docs/decisions/OWNER_DECISIONS.md). It is a callable native WordPress screen and controller for an exact private retention plan, the existing durable mail intent/manifest, owner evidence handoff, independent server readback and safe resume. It registers **no hooks, routes, cron jobs, public shortcodes or production providers**. Both lab flags, local WordPress and `http://bsre.invalid` are mandatory. It adds no Gmail permission, mailbox automation or deletion method.

## What an owner can do in the synthetic lab

1. Sign in as the explicitly configured WordPress owner with `manage_options`. A different administrator cannot access the review. Enter the authoritative closure ID and prepare the complete private exact plan.
2. Review its digest, admission/closure hashes and every resource. Approve that exact plan with an action-specific WordPress nonce. The controller commits approval, then the existing Workflow commits the mail intent before showing the manifest. Initial approval has the existing fifteen-minute window.
3. In the owner's separate mailbox procedure, identify the exact marketing mailbox copy using message ID, RFC822 Message-ID, fingerprint and enquiry identities. Perform only the approved exact-copy owner action and check Trash. Supply a private action-evidence reference and SHA-256 to the handoff form. This is an owner declaration, **not proof of absence**. There is no upload handler or automatic mail deletion.
4. The server invokes an independently injected `MailReadback` adapter with the stored manifest. Advancement requires an authoritative, fresh (at most 300 seconds), complete observation including Trash, bound to that exact mailbox/message/binding and no earlier than intent. UNKNOWN, provider errors, incomplete coverage, mismatched bindings, Trash copies and a missing search result all hold. `UnverifiedReadback` is the default and always holds.
5. Only accepted server readback produces the receipt consumed by `Workflow`. The receipt binds the authenticated owner, exact digest, message, full binding hash and declaration/readback evidence. Workflow independently rereads its original provider and rechecks closure, admission, scope and history before continuing. A signed-in checkbox or owner evidence reference cannot authorize absence. A false independent adapter claim cannot bypass Workflow's provider read.

The private page escapes identifiers and has labeled inputs, structured headings, status/alert text and keyboard-operable forms. `serve()` emits no-cache/noindex/referrer/CSP headers and sanitized failures. No plan, mailbox identifier, message content or evidence is written to a URL, external resource, browser storage, analytics or log by this implementation. The reopen form uses an opaque review ID in an authenticated lab GET; the full plan never comes from a request. GET never starts or resumes provider work.

## Explicit integration seam

Load `WordPress.php` from a deliberately protected local-lab harness. Create a dedicated `wpdb` connection with the exact prefix `owner_mail_review_synthetic_`; construct `WordPressStore($db)` and explicitly call `install()`. Construct `WordPressSession($nominatedOwnerId)`, `ReviewAuthority($store, $session)`, then the existing `ClosedRetention\Workflow` using that **same** authority and the reviewed journal/adapters/admission. Construct `Controller($workflow, $authority, $store, $session, $independentReadback)` and call `serve($controller)` only from the protected harness callback. No callback is installed by these files. The final adapter is a server dependency, never a request field; no authenticated production implementation is provided.

The custom InnoDB table stores private plans, declarations and accepted server receipts under opaque random review IDs. Connection-owned advisory leases and compare-and-swap revisions serialize a job. Approval and accepted receipt are committed and reread before Workflow advances. A lost acknowledgement can resume the same exact plan and receipt without repeated mailbox actions. Already accepted evidence cannot be replaced by a conflicting handoff. Storage errors do not establish success. The existing Workflow's independent closure lease/journal remains authoritative across stores.

## Recovery and private-record expiry

Unapproved UI jobs expire at the plan's initial fifteen-minute expiry. Approved UI caches expire at approval plus thirty days. Authorized requests call bounded `pruneExpired()` (100 expired records per call); it acquires each job lease, rereads expiry and removes only the corresponding revision. A dedicated local maintenance invocation is necessary when no owner visits the screen; there is no installed scheduler. Do not assume an idle database cleans itself. No UI cache expiry infers provider completion or removes authoritative unresolved closure evidence.

`Cleanup.php` provides a separate private cleanup screen/controller. It reads the exact plan from the authoritative Workflow Journal using an owner-supplied digest, so it still works after the duplicate UI cache is gone. The owner reviews that plan and separately authorizes `EXPIRE_PRIVATE_JOURNAL` through a digest-specific nonce. The grant exists for that one request only. Existing Workflow enforces the thirty-day recovery window, current readback/floor/history checks for completed jobs, and explicit manual reconciliation for unresolved jobs. Unresolved closure evidence remains authoritative; its eventual source-retention policy/reconciliation still requires deployment acceptance. No stale UI approval authorizes cleanup.

## Verification and open gates

Run `php -n tools/owner-mail-review/test_owner_mail_review.php` and `php -n tools/owner-mail-review/guard.test.php`. The focused tests execute actual rendered forms and the unchanged Workflow through declaration/readback/receipt/resume, CSRF and owner isolation, provider/Trash/binding failures, interrupted acknowledgements, restored resources and post-expiry cleanup.

`native-test.php` runs only after the isolated lab WordPress bootstrap, with this directory alongside `closed-enquiry-retention` and `consent-retention` under `/opt/lab/`. It uses real WordPress users/capabilities/nonces and a real MariaDB private review store, fresh-connection readback, leases, revision conflicts and expiry. Mail resources remain synthetic arrays. Passing pure tests or PHP lint does not claim this native harness ran.

Remaining gates: real protected closure ledger/collectors and exact-copy identifiers; authenticated complete mailbox observation without new scopes; reviewed owner/evidence custody and procedure; durable production provider integration; actual native runtime/interrupt/concurrency acceptance at the exact source head; supported backup/restore and scheduled private-cache expiry/reconciliation; independent review and separate production authorization. MailApp cannot supply inbox access or exact message IDs. The existing Intake26/Outcome40 contracts, baseline fixtures and Workflow are unchanged. Advertising remains paused.
