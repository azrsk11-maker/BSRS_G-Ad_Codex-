# Preference-retirement development candidate

This is an **isolated synthetic SQL implementation**, not a deployable retention release. No plugin hooks, scheduler, HTTP routes, production reads, deletions or permission changes are introduced. `PreferenceRetirement` refuses every database prefix except `retention_synthetic_`, every environment except `local`, and every home URL except the synthetic `http://bsre.invalid`; an explicit lab constant is also required. Apply remains disabled unless a separate test-only constant is set. Do not remove these guards to run against production.

The adopted policy is recorded in [OD-007](../../docs/decisions/OWNER_DECISIONS.md): preferences valid for180days; never-submitted choices retained12calendar months; closed/unsuccessful enquiries and matching emails retained12months after actual closure; monthly review; new encrypted owner-only recovery copies30days. Policy approval does not authorize a production purge.

`RetentionInventory.php` is the unchanged previously reviewed pure helper, SHA256 `5d7a68b6f40ccf3c87071382b2a392c91243b8d7378d668732ae3a6e759f89cb`. Its conservative policy holds all history while the latest subject choice is not yet due, or any capture exists. An unknown capture subject holds every candidate. Consequently this is not proof of exact per-choice deletion deadlines or full lifecycle coverage. Submitted evidence, active preferences, unresolved history, gaps, future times and uncertainty stay held. Leap-day anniversaries clamp to28February using Dubai time. Existing helper labels deliberately remain `SYNTHETIC_INCOMPLETE` and live linkage remains unverified.

The SQL adapter reads a bounded consistent snapshot of the actual three consent tables, with exact schema validation and a1000-row ceiling. Preview performs no deletions. A private plan binds the full snapshot, exact row references, scope and15-minute expiry. Apply requires administrator capability, explicit plan-digest confirmation and a locked snapshot that still matches. Changed data, altered plans, expiry, unknown links and nontransactional tables fail closed. All deletions and a minimal count/digest/actor audit commit together; failure rolls back. Plans contain pseudonymous references and must not be published or logged. Audit receipts contain no subject, request, contact, click or lead identifiers.

`build-candidate.mjs` verifies the exact captured consent-store hash before deriving a separate namespace candidate. It adds the missing state-row lock to `stage()` and rejects stale evidence after retirement. The original30-member plugin fixture stays untouched. Derivation performs byte transformations only at image build time; no WordPress/custom PHP runs before kernel isolation. Baseline native tests still use the original plugin, followed by separate candidate tests using only separate synthetic tables. Deadlocks between existing export lock order and retirement must remain fail-closed; production integration needs broader lock-order review and retry acceptance.

`tools/staging-lab/retention.php` tests real MariaDB transactions, scoped deletion, stale plans, rollback, accepted/in-flight holds, unknown links, calendar boundaries and two-process contention. A second database connection must be observed in `INNODB_LOCK_WAITS` before retirement commits; its stale stage must then fail. No real enquiry is submitted or email sent. The lab never deletes intake/outbox, Google Sheet, email or backup records.

Still required for a deployable release: complete historical intake/capture/outbox linkage and missing-evidence treatment; authoritative closure source; individual choice deadline/necessary-history reconciliation; current permission/withdrawal authority; owner-reviewed manifests; submitted evidence and matching-email deletion; encrypted30-day recovery and restore re-deletion ledger; integration packaging; scheduler/alert ownership; deployment approval and native/browser/platform acceptance. No production readiness is implied by green synthetic tests.

## Deletion ledger and restore rehearsal

`RetirementLedger.php` records exact retired history receipts and row hashes in the same transaction as deletion and its audit. A checkpoint serializes writers; a bounded sequence/hash chain detects missing, altered or truncated entries against a separately trusted latest anchor. The ledger/checkpoint are deliberately excluded from the three-table synthetic consent snapshot. Restoring those three tables cannot roll back the current ledger. This is a lab boundary, not proof that Hostinger whole-database recovery preserves an external authoritative ledger.

`backupSnapshot`, `ledgerAnchor`, `previewRestore` and `applyRestore` remain protected by the existing lab/admin/apply guards. A restore plan binds exact package metadata, snapshot bytes, current ledger anchor and15-minute approval. It requires a fresh30-day package, rejects a stale/future watermark and refuses to treat an old backup anchor as current authority. Re-deletion preserves later choices with different receipts, never deletes captures and holds restored captures referencing retired or unresolved evidence. Successful reconciliation still returns `reopen_authorized:false`; no service is reopened automatically. Re-deletion and its private count/digest/actor audit are transactional.

The native `restore.php` harness encrypts exact snapshot bytes with an ephemeral key through `backup-bridge.mjs`, restores only disposable consent fixtures, then reapplies later deletions. It tests ledger-write rollback, stale anchors, held captures, approval/expiry, restore rollback, preserved accepted evidence, newer choices and altered/truncated ledger refusal. Production snapshot merge/preservation, independent authenticated ledger custody/anchor freshness, protected expiry/compaction, complete historic linkage, closure and provider restore acceptance remain unimplemented. Ledger records have a30-day replay deadline; this candidate does not yet delete/compact expired private ledger rows. Do not claim full retention compliance from this rehearsal.

## Intake/capture/outbox linkage diagnostics

`LinkageReconciliation.php` assesses exact raw consent-capture columns and26-column deployed receiver rows, with1000-row/8MiB bounds and no writes. Receiver intake and outbox are the SAME row in the captured implementation; WordPress keeps the private consent sidecar rather than a second full lead database. Matching uses canonical request UUID plus exact lead/event receipts. Duplicate requests (including case aliases), reused receipt IDs, missing captures/receiver rows, unlinked receipts and payload integrity conflicts are held. Reports contain counts/reason codes, no request/lead/event identifiers, contact details, click identifiers or payloads.

WordPress fingerprint is SHA256 of the original request bytes; receiver fingerprint is SHA256 of its normalized JSON. These domains are deliberately not compared. Receiver payload integrity is checked against its own stored JSON/hash, and request/role identity must agree with the row. Receipt matches do not verify current permission, person qualification, actual mail delivery or historical coverage. Original measurement holds and unresolved outbox status are separate counts. An empty issue list is NOT deletion/import authority: every report permanently marks historical coverage, mail delivery, deletion and import authorization false. Caller-supplied completeness/production labels are rejected.

Fifteen focused PHP cases exercise gaps, duplicate identities, receipt reuse, raw-versus-normalized hashes, redaction, ambiguity and malformed/unbounded input. Actual WordPress-to-pinned-receiver interop adds eight checks using real synthetic sidecar and receiver rows. Session-filtered records prove that session only, never complete historical coverage. Production still requires authenticated complete consistent source collectors, missing-sidecar recovery, private current authority and email-copy evidence. No production collector, repair writer, purge or conversion upload is introduced.
