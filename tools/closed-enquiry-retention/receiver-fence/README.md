# Synthetic no-mail-copy retirement candidate

This extends the existing closure workflow for a due closed/unsuccessful enquiry that has never invoked the receiver's mail sender. It supplies no live mailbox, credentials, deletion method, deployment, scheduler or production authorization. The receiver is source-derived from the exact pinned Version2 fixture through the existing retention-admission builder; immutable fixtures, signed wire-v1, Intake26 and Outcome40 remain unchanged. `BSRE_SYNTHETIC_NO_COPY_LAB` must be an injected true capability and `ScriptApp` must be absent, so this candidate cannot run as a deployed Apps Script.

`closedNoCopyRetire(scope)` executes under the actual receiver ScriptLock. It requires the exact request/lead/event IDs, normalized payload fingerprint, closure ID/revision/hash and admitted configuration hash. The original row must have numeric attempt count zero, blank send/start timestamps and a non-sending status. SENDING, AMBIGUOUS and any attempted/reconciled send remain held. Fresh affirmative, complete marketing-mailbox absence including Trash comes from a separate trusted readback adapter; status and empty inventory cannot create it.

Fence issuance is a **trusted synthetic setup capability**, not an owner retirement workflow. No supported production coordinator currently acquires the closure Journal lease, verifies the authoritative CLOSED/UNSUCCESSFUL revision and twelve-month due date, obtains exact owner review/authority and then issues the receiver fence. A scope hash binds the supplied closure bytes; it does not establish their truth, due status or authorization. `Workflow::prepare()` independently checks closed/due/current closure under its Journal lease before preparing any purge plan, but it consumes an already issued fence. The test fixture calls that setup capability directly. A separately reviewed authenticated coordinator and protected closure producer remain prerequisites; this candidate adds no public retire route or grant.

The source writes and reads back an HMAC-authenticated per-request fence before changing the existing email-status cell to `RETIRED_NO_COPY`. Actual `doPost`, receipt-status recovery, `reconcileLeadEmail` and each `processLeadOutbox` row consult the fence under their existing ScriptLock. Healthy older queued rows retain delivery; retired or uncertain rows are deferred individually. Missing/corrupt fence readback cannot authorize a retention plan or requeue. A retained fence also rejects unknown append after synthetic row purge.

`Workflow` takes an optional fifth `NoMailCopy` adapter; the default is `UnverifiedNoMailCopy`. Only the exact `RETIRED_NO_COPY` closure status can select this branch. Zero email resources require the exact fresh provider proof; SENT still requires its original mail bindings and owner receipt path. The private plan pins the scope and stable fence/source/epoch/policy hashes. Every irreversible step, completion retry and cleanup revalidates provider evidence. Completion, completed retry and completed-job cleanup additionally require the receiver's actual row readback to be ABSENT; a contradictory RETIRED row cannot pass through another adapter's absence claim. Purging Intake removes its outbox in the same synthetic receiver row. History incompleteness and the existing nonidentifying admission floor remain mandatory.

## Runtime and recovery boundary

The injected synthetic runtime adapter returns fresh source/configuration/restore-policy hashes and the enforced retention-admission descriptor hash. Actual guarded receiver paths compare the independently current external floor with a separate **restorable metadata tab**: exact namespace, epoch, revision, admission generation/activation/audience and source/policy hashes must agree under ScriptLock. The metadata tab does not change Intake26. A new retirement advances the nonidentifying external epoch first, commits its signed fence/status, then stamps current metadata. Partial updates remain held. No production bootstrap, floor-reset or automatic adoption of restored metadata exists.

The bounded fence contains identifiers for thirty days. Removing it additionally requires a fresh custody receipt bound to the actual external floor, current store metadata, exact scope and fence, proving the approved backup window and expiry through the fence's creation time. Cleanup advances a monotonic nonidentifying pruned-history boundary and rotates both external/store epochs before identifier removal. A pre-retirement snapshot therefore retains an obsolete epoch. After identifier pruning, the synthetic reapplication helper refuses any nonempty obsolete store; a boolean cannot override that boundary. Current healthy old rows remain usable in the current store. Supported restore needs current complete-state provenance and retention reapplication; a raw manual row copy outside that path is not certified.

Before removing the fence, Workflow durably saves a source-HMAC signed cleanup intent in its existing private journal. If the receiver delete acknowledgement or subsequent journal deletion fails, that exact signed intent plus fresh floor/store/mailbox/custody readback permits idempotent completion. Missing fence alone remains unverified. The receiver stores no permanent per-request cleanup registry. An interrupted purge can scrub its duplicate fence/job only under the same recovery authority; its authoritative closure record remains for manual reconciliation. A failure before a cleanup intent is durably saved leaves the fence intact.

**This repository does not implement that real external authority.** Synthetic runtime and mailbox callbacks are test service doubles, not authenticated provider proofs. In particular, a `restore_fenced` value supplied by an arbitrary caller cannot certify a real restored Sheet, configuration, backup expiry or independent floor custody. Production current-store/restore authentication, backup/rollback enforcement, protected metadata, complete collectors and producer quiescence remain required before any live cleanup or sender reopening. Unsupported/expired backups, out-of-band manual writes and raw provider restore bypasses remain held; no permanent per-person/request registry is introduced to cover them.
