# Protected actual purge server ABI v1

This ABI is a new reviewed engineering contract, not an assertion that a provider has these endpoints or fields. `PurgeServiceTransport`, `Intake26Transport`, `Outcome40Transport` and `MarketingMailReadTransport` are protected server dependencies. No endpoint, credential, workbook/mail identifier or key is accepted from a browser. There is no default implementation or activation hook. Enroll exact server policy/source hashes and independent Ed25519 public keys through separately reviewed server configuration. The lead HMAC is not proof of custody/approval.

Every exchange receives `{contract: bsre-actual-purge-request-v1, actor, policy, source_hash, operation, challenge, body}`. Reply bytes must be canonical JSON with exactly `{key_id, statement, signature}`. The statement has exactly `contract=bsre-actual-purge-evidence-v1`, actor, policy, source_hash, operation, challenge, request_hash, issued_at, expires_at, result. `request_hash` and signed statement digest use the preserved PHP `Workflow::digest`. Signature is canonical-base64 Ed25519 over the ASCII lowercase SHA256 statement digest. Issuance must be in the past thirty seconds; expiry must be future and at most sixty seconds after issuance. Request challenge/source/policy/actor/operation/digest all match exactly.

- `approval`: body binds exact action and full reviewed plan. Result has actor, action, plan_digest, approved_at, approval_expires_at. The server independently authenticates the nominated owner and verifies exact manifest approval. Approval deadline is an immutable source fact, at most 900 seconds after approved_at; a fresh signed response cannot renew it.
- `boundary`: body binds action, closure_id, full plan or null, immutable grant or null, exact durable record or null, operation and binding or null. Result has request_hash plus true claims owner_approval, current_journal, current_sources, mail_and_trash, recovery_custody and history_floor. The server must obtain independently current signed anchor and decrypt the exact current encrypted journal. It verifies full closure, IDs, revision, plan/record/step/intent, twelve-month calendar eligibility when purging, non-shared identities, original wire v1/Intake26/outbox, exact source deployment/generation/admission, current sender fence and provider-complete copy/history/snapshot/recovery custody. A client boolean, caller record, caller anchor or lost reply is not evidence. For `forget_journal:readback`, exact authorized absence of the just-forgotten job is required, rather than presence of its old record. A stale/unavailable/partial/unknown surface rejects the operation. REVIEW can inspect only an authenticated owner context; it cannot grant mutation.
- `manual_mail_receipt`: body binds actor, plan_digest, message_id and current custody claim. Result has exactly receipt (null or the original nine-field owner-mail-receipt schema retained in Workflow). A receipt is issued only after independently checking the genuine owner's exact reviewed manifest/manual deletion evidence and current complete absence from marketing@blackswanrealestate.ae **and Trash**. It binds the original message/rfc822 identity, full content/copy fingerprint, manifest binding hash and observation not before durable intent. No automated physical mail deletion is exposed.
- `resource`: body has store (`intake`, `outcome`, `email`), operation (`inventory`, `read`, `remove_exact`), arguments, full current custody claim and idempotency_key. The key is null for reads; deletion binds digest of `{plan_digest, store, binding, intent_at}`. Result has request_hash, store, schema (`Intake26`, `Outcome40`, `MarketingExactMessageV1`), schema_hash, complete_surface, trash_included (true for mail, null otherwise), shared_identity_absent, metadata_bound, wire_v1_preserved, outbox_reconciled and result. All custody flags must be true. Inventory result is `{bindings:[...]}` bounded to 100; exceeding bounds rejects instead of truncating. Read result is `{state:PRESENT|ABSENT,binding:object|null}`; ABSENT means a complete exact scope search, never failure/null transport. Delete result is `{confirmed_absent:true,binding_hash}`. Email remove_exact must reject unconditionally on the service as on the consumer.

The consumer pins the canonical Intake26 header SHA256 0dcac495bed4beda7a027c5d21d0d8b1caaa8a307e6eb815e3566c46f41369ca and original Outcome40 schema-byte SHA256 bf477cc0cc4a161775abd702777898c6046d5dfcf0f2ae0e86fe078a3a63d9df in schema_hash; mail schema_hash is null. These are inspected contract hashes, not invented provider identities.

Intake provider operations must use exact reviewed Intake26 headers/source, complete request/lead/event identity search, original signed wire fingerprint, accepted-time match, actual sender status/attempt reconciliation and full row/metadata predicate. No row-number-only deletion, unbound occupied columns, formulas, notes, links, merged cells, protections or shared IDs may be accepted. An actual-domain no-copy resource requires current independently verified fence/copy custody, zero sends and exact durable approved intent. SENT resources require genuine exact copy reconciliation instead of a fabricated no-copy proof.

Outcome provider operations must use the exact reviewed forty-property schema and independently verified physical headers/complete row/metadata surface. The schema is not itself a statement of sheet column order. Resolve original and canonical lead/person/role linkages and shared-resource ownership from the provider-complete scope before destructive operations; conflicting or multi-request shared outcomes hold for owner review. Do not infer closure time/revision from Outcome40: the exact separate closure ledger supplies it. There is no financial-ledger deletion operation in this ABI.

Before dispatch the service must re-read exact source/binding and immutable owner grant against its actual current clock. It durably registers each stable deletion key before provider I/O, uses exact compare-and-delete, and reads back the complete authorized surface. A lost write acknowledgement or changed binding holds, and a repeated idempotency key reconciles the original outcome rather than issuing a second delete. Ambiguous operations are never certified absent. Fresh current source/mail/Trash/history/recovery custody is required at every destructive use including cleanup with an historical signed ticket. Restore fences and history-incomplete floors stay in force; no indefinite hashed-person register is created.

During the guarded SQL-committed/anchor-old interval, `boundary` additionally carries transition `{before,after,encrypted_body}` only for `journal_anchor_advance` and its readback (null for ordinary operations). This is an explicit custody phase. The service independently reads the committed row, verifies exact revision/hash/ciphertext and `after.revision=before.revision+1`, matches the retained prior signed anchor/hash, decrypts the candidate and verifies the sole allowed state delta under the same immutable grant and current source/mail/Trash/recovery authority. REVIEW may never authorize a journal mutation/transition. Initialization/collection remain separately approved upstream guarded bootstrap operations. A purge may change only that job's next revision and allowed monotone history/admission fields, retaining existing start/completion deadlines; a newly absent job must start before the actual current plan expiry, after approval, using a fresh timestamp; expiry may remove only the exact due COMPLETE job/closure. Before CAS the independently current anchor must equal before; afterward it must equal after. Any disagreement or unrelated state change holds. The service uses an independent committed-state view, never the caller transaction's uncommitted read. Ordinary boundaries continue requiring the current stable anchor/ciphertext.
