# Offline tracking contract prototype

This dependency-free Node module is development evidence. It is **not deployed, a Google tag installer, a browser SDK, a production permission authority, or an offline import client**. It makes no network calls, reads no cookie/local storage, changes no website/account, and writes no lead or financial record.

`contract.mjs` supplies:

- An explicit reviewed campaign/page/CTA registry. Unresolved planning rows do not become actual URLs or metadata. Current fixture paths are synthetic planning examples, not published pages.
- A strict input key allowlist and registry-derived public payload. Names, email, phone, free text, arbitrary URL/referrer/UTM fields and query/hash-bearing URLs are rejected. Private lead/evidence/permission metadata stays internal; a supported opaque transaction ID is sent only in the simulated Ads payload.
- Independent analytics/advertising permission checks. Unknown, malformed, expired, unverified, ineligible, admin or QA contexts deny measurement. Enquiry intake is outside this module and remains possible without measurement permission.
- Advertising-only capture of exact `gclid`, `gbraid`, `wbraid` values without granting analytics. The 512-character alphanumeric/underscore/hyphen bound is a conservative local supported-input rule, not a claim about every Google identifier limit. Unsupported values reject; they are never trimmed, lowercased, truncated or fabricated. Captured IDs never enter this prototype's GA4 payload.
- A legacy `bsre_lead_accepted`/`form_submit` to v3 `form_accepted` adapter requiring durable server-confirmed receipt evidence. It maps once to GA4 `generate_lead`; native Ads accepted-enquiry preparation requires its own reviewed destination and stays Secondary. Retried events cannot upgrade the original analytics, advertising or ad-user-data decision.
- Specialized CTA normalization, navigation identity for page views, and an atomic in-memory reservation ledger. Same ID/same payload suppresses; same ID/changed payload conflicts. All destination validation happens before reservations. Status is `prepared_only_not_delivered`, never delivery success.
- Reviewed native Ads route plus supported `transaction_id` mapping requirements. Custom `event_id` is not treated as universal destination deduplication. Google documents duplicate handling for the same conversion action and transaction ID in [Google Ads Help](https://support.google.com/google-ads/answer/6386790).
- Strict evidence-source requirements for calls/conversations, bookings, qualification, transactions and commission. Browser clicks cannot establish these outcomes. Commercial outcomes remain withheld with `REVIEWED_OFFLINE_ADAPTER_REQUIRED` even with simulated evidence.

Google's [consent setup documentation](https://developers.google.com/tag-platform/security/guides/consent) distinguishes `ad_user_data` from storage permission. This prototype therefore requires both current and originally captured ad-user-data permission before preparing the accepted-enquiry Ads payload. It does not implement Consent Mode, a consent banner, signature verification or Google runtime behavior.

## Required before production use

1. Replace all synthetic fixtures with approved, evidence-backed native registry values; bind stable metadata in the real CMS and preserve public-main-site continuation. The current URL validator deliberately supports only reviewed `/lp/bsre-c####/` and existing `/enquire/` routes; arbitrary main-site path coverage needs a reviewed route registry, not a permissive regex.
2. Supply cryptographically authenticated server eligibility, actual original/current permissions and durable acceptance. The JavaScript booleans/evidence objects are trusted test inputs, not security proof. Never expose this API as a public acceptance authority.
3. Reconcile legacy event semantics and old wire-1 receipt fields. The new `original_ad_user_data` requirement and strict `bsre-event-<UUIDv4>` opaque Ads transaction identifier are intentionally not evidence that the deployed receiver already provides these shapes; a reviewed compatible adapter or explicit held state is necessary. Never rewrite or fabricate an existing identifier silently.
4. Implement durable dispatch/outbox state, concurrency safety, same-ID retry and reconciliation across browser reloads/server restarts. The in-memory ledger resets with the process and cannot establish production GA4 or Ads deduplication. A shared producer identity is required to prevent generic/specialized duplicate clicks; different fabricated IDs cannot be correlated by this prototype.
5. Use the account's actual verified action/tag configuration, provider-supported dedup field, consent behavior and full-payload diagnostics. Default Google automatic fields, enhanced measurement, referrers, storage and SDK URL handling are not exercised by unit tests. Do not import the same accepted receipt from GA4 as a second Ads action.
6. Maintain separate GCLID-only qualified-outcome export approval and actual Data Manager capability. This module neither uploads outcomes nor validates finance/qualification records. Names/contact data never belong in its analytics payload.
7. Complete browser/native/security/recovery acceptance and separate owner authorization before any production write.

Run `node --test tracking-system/contract.test.mjs` from the parent directory. Sixteen tests passed in the combined run recorded in the audit. Fictional IDs such as `G-TESTONLY00` and `AW-999999999/testonly` exist only in unit fixtures; no Google endpoint is called.

## Private session-only first/latest advertising attribution

`attribution-state.mjs` adds a pure state reducer and private durable-receipt context. It preserves first/latest acquisition snapshots across internal navigation; only explicit trusted verified external-acquisition evidence and a reviewed campaign/page registry binding can create a new touch. Unknown URLs, self-referrers and UTMs do not establish acquisition authority. Test booleans are not cryptographic verification.

Exact `gclid`/`gbraid`/`wbraid` bytes and optional six UTM / three Google-ID strings remain private. Unknown fields, controls, unsupported values and oversize reject instead of truncating; missing values stay absent. Numeric Google identifiers remain strings, not invented resource bindings. Bounded UTM text may still contain contact/free text and is **not certified safe for disclosure**. No private attribution object is passed into GA4 or the existing public event normalizer.

This state uses the advertising purpose independently of analytics. Advertising-only consent works; the separate pure analytics path and accepted-receipt consumer are described below. State is session-only: session changes, expiry, denial, admin/QA or unverifiable permission prevent reuse. Withdrawal clears the owned reducer state even if configuration is unavailable. The caller must replace its slot with the returned `next_state` and dispose of old copies; immutable JavaScript snapshots cannot erase arbitrary prior references. Original touch permissions survive retries without upgrades.

Eleven focused tests cover A → internal public navigation → B → private accepted receipt, metadata/ID exactness and immutable snapshots, consent/session/withdrawal boundaries, evidence/registry validation and retries/conflicts. Native website persistence, main-site route bindings, authenticated acquisition/consent/receipt evidence, compatible wire-v1 sidecar packaging, durable dispatch and live WT-017 acceptance remain open. This is independently testable development progress, not completion of the full attribution contract. Run `node --test tracking-system/attribution-state.test.mjs`; mandatory repository CI discovers it automatically.

## Composed enquiry client attribution candidate

`build-attribution-client-candidate.mjs` extends the source-pinned receipt client. It retains analytics acquisition across same-origin navigation and queryless continuation where the site's referrer policy removes the referrer. The current service page remains the enquiry's `landing_page`.

Purpose-specific snapshots receive a private correlation UUID and a shared capture-time value only when newly captured together. The combined wire context merges analytics metadata with an ad-bearing snapshot only when those values and the captured landing page match. A later click cannot inherit an older source's UTM values or referrer. Legacy snapshots without the private UUID cannot establish alignment. The UUID stays in owned session state and is stripped from the wire payload. It grants no permission or trusted Google acquisition identity.

Seventeen focused attribution cases cover actual client execution, internal navigation, later captures, mixed-purpose separation, legacy state, UUID failure, delayed grant, withdrawal/regrant, expiry, ineligible/QA inputs, blocked storage and immutable retries. Seven existing receipt regressions also pass. The isolated WordPress client harness consumes this composed candidate, while retaining its synthetic TEST exclusions. That harness establishes recovery compatibility; consented WordPress attribution, native browser storage and live Google delivery remain separate acceptance work. A new parameter-bearing URL with no referrer remains an observed attribution hint with uncertain external origin.

The existing common-wire policy still prioritizes a snapshot carrying an advertising click over a later analytics-only snapshot. Separate purpose histories remain in private session state. Transport of complete independent-purpose histories requires a reviewed contract change and is still open.

## Private purpose-separated accepted-receipt sidecar

The composed client above already captures analytics independently. `analytics-attribution-state.mjs` and `private-purpose-sidecar.mjs` address a different contract gap: consuming complete independent-purpose first/latest histories at the **private accepted-receipt boundary**, without combining a newer analytics source with an older advertising click. They add no browser producer, storage, live tag, wire-v1 field or public analytics event.

The pure analytics reducer uses the existing reviewed campaign/page registry and an explicit source catalog. Only supplied standardized UTM business codes that exactly match that catalog are retained; missing fields remain absent. Click IDs, advertising resource IDs, raw URLs/referrers, arbitrary fields, encoded text, contact syntax and free-form text are unsupported. Catalog syntax is deliberately narrow and is **not a PII detector**: a qualified reviewer must establish that its exact business codes are non-sensitive. Source catalogs, consent booleans and evidence references are trusted test inputs, not authenticated approvals. Changed source versions or invalid evidence hold reuse. Unknown new touches require the current capture timestamp; only already-known identical retries may use an earlier observation. Delayed/backdated new observations need an authenticated original-capture adapter and remain unsupported, rather than being reconstructed under a later grant. No actual source catalog or production identity is supplied.

`PrivatePurposeSidecarLedger.prepare(owned, receipt, evidence, configuration, original_capture)` consumes the new analytics reducer and the unchanged advertising API with one current session/clock. Its mandatory version-1 original-intake envelope separately supplies the original session/time, lead/event identities, captured consent and both captured histories, with a trusted evidence reference. Missing or inconsistent original capture holds; current navigation is never substituted. It validates histories at capture time, refuses touches after capture and matches original receipt permissions. Its private sidecar retains each purpose's own first/latest snapshots. First preparation after another acquisition therefore still uses the supplied original intake history. Same receipt retries preserve that original capture; changed receipt/lead identities, permission flags or capture bindings conflict. A later grant cannot fill an originally absent accepted context. Returned current `next_state` remains separate.

`withdraw(owned, purpose)` clears only that cached purpose before caller-state validation, without configuration or receiver access. Every preparation observes the common session/clock/permission and sweeps **all receipt slots** for foreign sessions, expired original snapshots or denied purposes before unrelated receipt/other-purpose validation can fail. A session A → B → A cycle, expiry or regrant cannot revive another receipt's context. Only SHA-256 capture/fingerprint digests and opaque bindings remain after context clearing; raw touches, ad IDs and UTM bytes are not embedded in retry fingerprints. Unkeyed digests provide consistency, not authentication. `contextCounts()` exposes only fixed aggregate counts for lifecycle diagnostics. The caller must replace its owned state and dispose of old returned copies; JavaScript cannot erase arbitrary prior references. This cache is measurement context, not the protected server consent-evidence register.

The in-memory ledger is capped and has no restart persistence, browser bridge, durable delivery/idempotency or consent-evidence retention authority. It is not an intake handler and cannot establish a genuine accepted enquiry. Production requires authenticated acquisition/permission/receipt inputs, approved non-sensitive catalog values, a reviewed backward-compatible private transport, durable custody/recovery and full native acceptance plus separate authorization. The existing client/common wire, signed v1 body, Sheet schema and GA4/Ads mappings are unchanged; installed integration and WT-017 remain open. Sidecars are rejected as public event fields and make zero network calls.

Run `node --test tools/website-tracking/tracking-system/private-purpose-sidecar.test.mjs` from the repository root. Twenty-three synthetic cases passed with no skips; existing mandatory tracking CI discovers the file automatically. Cases cover independent histories, exact reviewed metadata, private-only output, original-capture/receipt conflicts, later navigation and retries, purpose refusal/withdrawal, global session/expiry clearing, unrelated failures and immutable snapshots. This is development acceptance, not live conversion or permission validation.
