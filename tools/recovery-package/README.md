# Encrypted synthetic recovery-package candidate

The separate [disabled synthetic expiry runner](expiry-runner/README.md) prepares bounded retry/restart/alert orchestration around this unchanged per-file helper. Real scheduling, durable custody and alert delivery remain unimplemented and require acceptance.

This module implements an isolated part of [OD-007](../../docs/decisions/OWNER_DECISIONS.md): new encrypted owner-only recovery copies expire after30days. It does not contact a provider, read a real website/database, hold real records, persist keys, create a production backup, schedule expiry deletion or authorize a restore. Real key custody, provider settings, recovery publication and platform acceptance remain separate gates.

Node built-ins only; compatible with Node18+. No installation is required. A supplied fresh, dedicated32-byte encryption key and random12-byte nonce are used with AES-256-GCM and a16-byte authentication tag. The caller must generate and protect the key independently; this module does not prove key freshness or ownership and must never store a key alongside its package. Secrets and package contents are never logged.

`sealPackage(snapshotBuffer, key32Buffer, {nowMs, deletionLedgerWatermark})` returns an encrypted Buffer. `openPackage(packageBuffer, key32Buffer, {nowMs})` authenticates and returns `{snapshot: Buffer, metadata, restoreAuthorized: false}`. Metadata fields are exactly `version:1`, `source:'SYNTHETIC_BSRE_LAB'`, `createdAtMs`, `expiresAtMs`, `snapshotSha256` and `deletionLedgerWatermark`. The SHA256 covers the exact snapshot bytes; expiry is exactly30days after creation. Metadata, its binary framing, ciphertext, nonce and tag are authenticated. Snapshot size is1byte–8MiB. Keys, metadata, watermark, sizes, timestamps, expiry/clock rollback, malformed encoding and authentication failures are rejected without returning plaintext. There is no supported production source label.

The watermark is the deletion-ledger sequence at snapshot capture, **never proof of the newest deletion state**. Restoration must separately acquire and authenticate the latest authoritative external ledger anchor, reconcile its sequence/chain and replay later deletions before reopening any service. An old ledger included in a backup is insufficient. This module deliberately returns `restoreAuthorized:false` even after successful decryption.

`writeOwnerOnlyPackage(directory, filename, snapshotBuffer, key32Buffer, options)` optionally seals and writes a new file. It requires POSIX owner identity, an existing current-user-owned0700 directory without symlink components and a simple basename. It creates only a new0600 file using exclusive/no-follow flags, checks inode/ownership/modes, syncs the file and refuses overwrite or symlinks. It does not create directories or change existing permissions. Unsupported Windows enforcement fails closed; Windows needs a reviewed ACL adapter. These checks assume a trusted same-user process and OS, not protection against root or a hostile owner. The synthetic helper does not certify a hosting provider’s backup ownership.

`deleteExpiredOwnerOnlyPackage(directory, filename, key32Buffer, {nowMs})` is an explicitly invoked synthetic expiry cleanup. It uses the same protected directory boundary, opens the existing regular0600 owner file without following links, bounds reads and authenticates GCM metadata/ciphertext before considering deletion. This private authentication path permits expired metadata solely to confirm an expired encrypted package; expired plaintext is cleared and never returned. Before expiry it refuses deletion. Wrong keys, tampering, symlinks, unexpected ownership/modes, inode/size/time changes and directory changes fail closed. At/after the authenticated30-day expiry it unlinks only the checked package pathname and returns `{deleted:true, expiresAtMs, productionAcceptance:false}`. Its path checks assume a trusted owner/OS; Node pathname operations cannot constitute an atomic hostile-owner inode-conditional unlink guarantee. No existing file is overwritten.

Run `node --test tools/recovery-package/package.test.mjs`. Tests use fabricated snapshot bytes, random ephemeral in-memory keys and disposable temporary files. Windows tests explicit unsupported guards; Linux must exercise actual0600/0700 ownership, overwrite, parent/file symlink rejection, before-expiry hold, tamper/wrong-key hold and authenticated expiry deletion. No real recovery copy or production deletion is performed. A provider scheduler, deletion failure alerts, key rotation/destruction, encrypted export transport, retention-log recovery and a genuine provider restore rehearsal are not implemented here.
