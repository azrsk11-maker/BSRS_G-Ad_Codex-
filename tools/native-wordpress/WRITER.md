# Disposable native draft writer

`native-draft-writer.php` is an inert synthetic-lab implementation. Including it registers no hooks, route, endpoint or UI. It has no production mode and does not extend the read-only `native-draft-preview.php` into a deployment handler. Actual CMS bindings, installed-template acceptance, content evidence and separate production authorization remain required.

The writer requires explicit enablement, a CLI administrator and nonce, the disposable `bsre_synthetic` database with `synthetic_` tables, fixed `http://bsre.invalid` WordPress constants, disabled external HTTP/cron, a non-root process, a read-only WordPress application, and a Linux network namespace with only loopback and no IPv4 route. These checks supplement the isolated lab's pre-bootstrap kernel isolation checks. They are deliberately incompatible with the live site.

Call `initialize($nonce)` explicitly to create the InnoDB journal. A separate `bsre-native-draft-lab-v1` manifest must use `SYNTHETIC_LAB_ONLY`, the fixed synthetic origin, and an explicit `pages` allowlist. Each entry supplies its reviewed campaign/landing pair, an existing draft parent CMS ID and exact parent state hash, a slug and complete synthetic path. The parent must carry `_bsre_native_lab_parent` with the schema value. The writer validates the reviewed registry's identity digest. It never creates a parent or derives a production route from the planning manifest.

`apply($manifest, $request, $nonce)` supports one `create`, `update` or `restore` operation. Requests include a unique operation key and the expected CMS ID, full state hash and latest native revision ID. Creation requires absence. Updates require a draft created by this writer with exact metadata, parent and path. Unmanaged pages, route collisions, published pages, duplicate identities and changed parents are held. Only inert, explicitly marked synthetic title/content/excerpt fields are accepted; there is no status, template, theme, global setting, Ads or measurement write field.

Before mutation, a durable `PREPARED` journal records the request digest and full native before state. An advisory lock serializes writer calls. A SERIALIZABLE transaction locks the complete small synthetic posts/postmeta ranges, covering parent edits and new ownership rows as well as the target. A dedicated `wpdb` subclass disables automatic reconnection so a native statement cannot silently retry on an unlocked session. WordPress's native insert/update/revision APIs perform the change. A readback requires enabled revisions, an exact latest revision matching the content, and an advancing revision when content changes, before the after state and `APPLIED` journal commit. Snapshots include the full native post row, metadata row identities/bytes and the complete native revision rows. Receipts expose both state/content hashes, CMS ID and exact before/after revision IDs.

Replaying an operation after a lost acknowledgement returns its stable recorded receipt only while the current state still equals its committed after state. Reusing an operation key with changed input fails. A rolled-back `PREPARED` operation can resume only from its exact before state. Any intervening edit requires reconciliation; retries do not overwrite it. A transaction/commit error must be treated as ambiguous by the caller: retry the identical operation key to inspect the durable result, never allocate a replacement key blindly.

Restore accepts a specific applied create/update journal reference and its exact current after state. An update restore writes the original three content fields under the same CMS ID and records a new native revision when content changes, preserving history rather than fabricating an old revision identity. Restoring a no-op update preserves the existing revision and reports `PRIOR_CONTENT_ALREADY_PRESENT_NO_NEW_REVISION`. A create restore retains the created draft, its content and revision trail, adds a durable reconciliation hold, and reports `HELD_CREATED_DRAFT_REQUIRES_RECONCILIATION`. It explicitly does not restore prior absence. The hold blocks further new operations; its existing restore operation remains replayable. Restore itself has an idempotent operation key and before/after receipt. There is no delete or trash API.

The native acceptance harness is `tests/native-draft-writer-test.php`. Copy it alongside the writer and `native-page-manifest.json` under `/opt/reviewed/`, and run it after `tools/staging-lab/native.php` installs the isolated database. It bootstraps only `/opt/wordpress/wp-load.php` after checking the network-none/non-root preconditions. It exercises real WordPress tables/revisions; create/update/restore acknowledgement replay; exact/disabled revision checks; second-connection parent-metadata and new-ownership contention; unmanaged/published preservation; injected post-write rollback; a killed database session before native insertion and exact prepared retry; and intervening-edit rejection. Content tests reject SVG, event attributes, input elements and shortcodes using a positive paragraph/emphasis allowlist. Output contains aggregate named checks only. These specific failure injections do not prove every process crash, commit-acknowledgement loss, storage failure or provider behavior. Ambiguous outcomes require durable journal/state reconciliation; a new operation key is never a recovery shortcut. A passing isolated test establishes disposable native behavior; it does not establish production readiness or approved page content.
